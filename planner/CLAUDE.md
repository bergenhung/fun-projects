# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A native multiplatform (iPhone + Mac) daily planner: SwiftUI + SwiftData, hourly grid view with day navigation, voice task entry, timed reminders, automatic completion check-ins, and recurring tasks. Full requirements live in [weekday-daily-planner-spec-v2.md](weekday-daily-planner-spec-v2.md) — read it before making feature decisions, especially the "OUT of scope for v1" section and the milestone build order. That spec file has changed more than once (grid range, reminder default, day navigation and recurring tasks moving from out-of-scope to in-scope) — always re-read it rather than trusting this doc's memory of an older version.

Note: this `planner/` directory is a subproject inside a larger personal monorepo (`fun project/`) containing unrelated Python projects. Nothing outside `planner/` is relevant to this app.

## Build system: XcodeGen, not a hand-edited .xcodeproj

The Xcode project is generated from [project.yml](project.yml) via `xcodegen`, not edited directly.

- **Never hand-edit `Planner.xcodeproj`** — it's regenerated and any manual changes are lost.
- After adding, removing, or renaming any file under `Planner/`, or changing target settings, regenerate:
  ```bash
  xcodegen generate
  ```
- `project.yml` defines one target block (`platform: [iOS, macOS]`) that XcodeGen expands into two real Xcode targets/schemes: `Planner_iOS` and `Planner_macOS`. Both share the same `Planner/` source tree.

## Commands

Build (no simulator needed for compile checks):
```bash
xcodebuild -project Planner.xcodeproj -scheme Planner_macOS -destination 'platform=macOS' build
xcodebuild -project Planner.xcodeproj -scheme Planner_iOS -destination 'platform=iOS Simulator,name=<device name>' build
```

Run in iOS Simulator headlessly (no Xcode GUI):
```bash
xcrun simctl list devices                                   # find/confirm a device id
xcrun simctl bootstatus <device-id> -b                      # boot + wait
xcrun simctl install <device-id> <path-to-.app>              # .app is under DerivedData/.../Build/Products/Debug-iphonesimulator/
xcrun simctl launch <device-id> com.wphuang.Planner
xcrun simctl io <device-id> screenshot out.png                # visual verification
```
`xcrun simctl launch`/`install` occasionally hang past a normal timeout on this machine for no clear reason — run them with `run_in_background` and pick the result up from the task notification rather than assuming failure.

There is no test target yet.

## Rebuilding without losing data

`xcrun simctl install <device-id> <path-to-.app>` over an already-installed app updates it in place — same as a normal App Store update — and **preserves the on-disk SwiftData store**. Use this for every routine rebuild-and-reinstall during verification.

`xcrun simctl uninstall` destroys the app's container, including the SwiftData store, entirely. Only use it when a genuinely clean slate is actually needed (e.g., specifically testing first-launch/empty-state behavior) — never as a routine step of "rebuild and check it still works." This matters more than it looks: earlier in this project's history, renaming model fields (`seriesID`→`recurrenceParentId`, `recurrence`→`recurrenceRule` with a type change) broke SwiftData's automatic lightweight migration for anyone with an existing store, since renames aren't something lightweight migration infers — combined with routine `uninstall`-before-`install` during testing, that's an easy way to silently lose real data.

**Past incident — real data loss reported by the user, recurring more than once, root cause not fully confirmed but mitigated**: the user reported all their tasks disappearing after an update, more than once, despite the schema having been stable (no field renames) in the turns between reports. Two structural weaknesses were found and fixed together, since either one on its own could plausibly explain it:
1. `PlannerApp.init()` used to `fatalError()` if `ModelContainer(for:configurations:)` threw for *any* reason. A crash-looping app is exactly the situation that pushes a user toward "just delete and reinstall it" — and *that* action, not the underlying error, is what actually destroys the on-disk store. If this was the real mechanism, the store itself was likely never corrupted; it just became inaccessible behind a crash, and the user's own recovery attempt is what finished the job.
2. The container was built from a bare `Schema([PlannerTask.self])` with no `VersionedSchema`/`SchemaMigrationPlan`, i.e. fully dependent on SwiftData's automatic lightweight-migration inference with no way to reason about or test what it does on an unexpected store shape.

Fixed in [PlannerApp.swift](Planner/PlannerApp.swift) and [Planner/Support/PlannerSchema.swift](Planner/Support/PlannerSchema.swift): the schema was made explicitly versioned (`SchemaV1: VersionedSchema` + `PlannerMigrationPlan: SchemaMigrationPlan`), and `ModelContainer` init failure no longer crashes the app — it falls back to `sharedModelContainer = nil` and shows a `DataLoadErrorView` explaining that the data is most likely still on-disk and that deleting/reinstalling the app is the one thing that would actually lose it, instead of doing that automatically via a crash loop.

**Verified**, not just theorized: switching to `Schema(versionedSchema:)` risked itself looking like an incompatible store to data created under the old plain-`Schema([...])` code — that would have been a self-inflicted repeat of the same bug. Tested directly against the simulator's real accumulated test data via a temporary `-debugDumpAllTasks` launch-argument harness (same pattern as the `-seedRecurringTest`/`-seedEditScopeTest` harnesses referenced below: added to `PlannerApp.swift`, fetches and dumps every `PlannerTask` row unconditionally so a check isn't accidentally scoped to "today" and blind to real data sitting on other dates, run once, then removed): installed the new build over the existing store without uninstalling, launched with the flag, and confirmed pre-existing tasks loaded correctly with their original titles/dates/times intact.

**Past incident #2 — real crash log obtained, root cause identified and fixed**: this recurred (user: "My planner app just crashed and all data are wiped out"), this time on the Mac app during normal everyday use, not right after an install — ruling out incident #1's crash-loop-on-launch theory, since this app had been running fine for ~12 hours (per the crash log's `procLaunch` timestamp) before crashing. Unlike incident #1, a real crash log was available this time (`~/Library/Logs/DiagnosticReports/Planner-*.ips` — macOS crash logs are `.ips` JSON, readable directly; check there first before re-theorizing if this happens again). It showed `EXC_CRASH`/`SIGABRT`, an *uncaught Objective-C exception* (not a catchable Swift `Error` — the same class of bug as the mic crash below) thrown from CoreData's `_PFFaultHandlerLookupRow` while fulfilling a fault, called from `-[NSApplication _handleDeactivateEvent:]` — i.e. it fired specifically when the Mac app lost focus, which is what triggers SwiftData's implicit context autosave.

Root cause: `PlannerTask.recurrenceRule` was stored directly as a Codable `RecurrenceRule?` — a struct wrapping `RecurrenceFrequency`, an enum with an associated-value case (`.custom(days: [Weekday])`). SwiftData's automatic storage for an enum-with-payload turned out to be broken: inspecting the on-disk SQLite schema showed columns for the no-payload cases (`ZDAILY`, `ZWEEKLY`, `ZWEEKDAYS`) but **no column at all for `.custom`'s `days` payload**. Confirmed directly (not just inferred) with a standalone `swiftc`-compiled harness reusing the real model/schema files outside the app: inserting a task with `.custom(days: [.monday, .wednesday, .friday])`, closing, and reopening showed the day list silently discarded — a real, reproducible bug independent of whether it's the *exact* crash trigger. (A direct headless repro of the crash itself wasn't possible — `_handleDeactivateEvent:` only fires inside a real running `NSApplication`, which a standalone script doesn't have, and this environment has no accessibility access to drive the real Mac app's UI to test interactively; see Testing section below.)

Also relevant: there were **no explicit `context.save()` calls anywhere** in the mutation paths (`AddEditTaskView`, `ContentView`'s toggle/delete/retime, `VoiceEntryView`) — every create/edit/delete relied entirely on SwiftData's implicit autosave. That means any crash in autosave (regardless of exact trigger) silently discards *everything* created or changed since the last successful autosave, with no error surfaced anywhere — a structural gap independent of the specific `.custom`-recurrence bug, and consistent with the store showing zero committed rows despite ~12 hours of normal use.

Fixed two ways:
1. **Removed all Codable-enum-with-associated-value storage from the model.** `PlannerTask` now stores recurrence as flat, primitive-only fields (`recurrenceFrequencyRaw: String?`, `recurrenceCustomDays: [Int]`, `recurrenceEndDate: Date?`) instead of a `RecurrenceRule?` blob; `recurrenceRule` is now a *computed* property bridging to/from those fields, so `RecurrenceEngine`/`SeriesEditor`/`AddEditTaskView`/`ContentView` all keep reading/writing `task.recurrenceRule` unchanged — SwiftData itself never sees `RecurrenceRule`/`RecurrenceFrequency` anymore. Verified via the same standalone harness that the `.custom` day list now round-trips correctly (insert → close → reopen → fetch), where the old shape silently lost it.
2. **Added explicit `try? modelContext.save()`** right after every mutation in `AddEditTaskView.save()`/`.delete()`, `ContentView.toggleComplete`/`delete`/`deleteSeries`/`applyRetime`, and `VoiceEntryView.createTask()` — so changes are durably persisted immediately rather than depending on implicit-autosave timing. This doesn't *catch* an Objective-C exception (nothing in Swift can — see the mic crash below), but it shrinks the window of unsaved, at-risk data to a single mutation instead of an entire session.

This is genuinely a **SchemaV2**: `PlannerSchema.swift` now has `SchemaV1` (frozen, with its own nested `@Model` class matching the exact old on-disk shape — including the old `recurrenceRule: RecurrenceRule?` — kept only so the migration plan has something to migrate *from*) and `SchemaV2` (current, flattened; what `PlannerApp.swift` actually targets). The migration stage is `.lightweight`, deliberately *not* `.custom`: a custom stage's `willMigrate`/`didMigrate` closures would need to fetch and read the old `recurrenceRule` to carry it forward, which re-triggers the exact fault-fulfillment path that crashes on a `.custom` value — attempting a "complete" migration could crash on the very data it's trying to rescue. Lightweight migration just drops the old column without decoding it, which is safe. **Tradeoff, disclosed here since it's a real behavior change**: any task that *was* recurring reverts to a plain one-off task after this migration (title/date/time/notes/completion all carry over fine; only the repeat setting resets) rather than risking another crash to preserve it. Verified via the standalone harness (old-shape store → open with `SchemaV2` + `PlannerMigrationPlan` → fetch) and, more importantly, against the simulator's real multi-session store, confirming the migration itself doesn't crash and non-recurring tasks (all of them, in the data available to test) carry over with titles/dates/times fully intact.

**What couldn't be verified**: whether `.custom` recurrence was truly *the* trigger for this specific crash (vs. some other autosave/fault interaction) — a direct headless repro attempt (fresh insert, close, reopen fresh as a fault, mutate, save) did *not* crash, only silently lost the `.custom` payload; the real crash needs a live `NSApplication` losing focus, which this environment can't drive. What's fixed either way: the confirmed data-loss bug, the general class of fragility (Codable enum-with-payload directly in a SwiftData model), and the "single implicit autosave is the only thing standing between a mutation and durability" structural gap. If this recurs a third time, check `~/Library/Logs/DiagnosticReports/Planner-*.ips` first — it settled this investigation far faster than re-theorizing did — and don't assume this exact fix is incomplete without that evidence.

`PlannerApp.swift` seeds three sample tasks (including an intentionally overlapping pair and one pre-completed task) when launched with `-seedSampleData`, e.g.:
```bash
xcrun simctl launch <device-id> com.wphuang.Planner -seedSampleData
```
The seeded hours are clamped into `GridConfig`'s visible range, so they always render regardless of what time it actually is when you run this, and they're scheduled on today's date. This writes to the real on-disk store like any other task creation, so it's additive on top of whatever's already there — it doesn't replace or clear existing tasks.

## Physical-device / signing notes

`project.yml` does not set a `DEVELOPMENT_TEAM`. Running on a real iPhone requires picking a signing team in Xcode's Signing & Capabilities UI, which XcodeGen will **wipe on the next `xcodegen generate`** unless the team ID is added to `project.yml`.

## CloudKit sync is prepared but not wired in

`PlannerTask` has inline default values on every non-optional property (`var isCompleted: Bool = false`, etc.) specifically because SwiftData requires that for a model to be CloudKit-syncable. That part is safe and already done.

The rest is deliberately **not** turned on, because it requires a paid Apple Developer account the project doesn't have yet, and enabling it without one would break the app: a `ModelConfiguration(..., cloudKitDatabase: .automatic)` needs a matching `com.apple.developer.icloud-services` entitlement backed by a real provisioning profile, and a half-configured CloudKit setup would fail `ModelContainer` init.

`PlannerApp.init()` no longer `fatalError()`s on `ModelContainer` init failure (see the "Rebuilding without losing data" section above for why that was changed) — it falls back to a `DataLoadErrorView` instead. That means a half-configured CloudKit setup would now degrade to that error screen rather than crash-loop, which is strictly better, but it's still not the desired end state — a user without a properly provisioned build should get a working *local-only* app, not an error screen either. Step 3 below covers this.

To actually enable it once there's a Team ID:
1. Add `DEVELOPMENT_TEAM` to `project.yml` and add an `entitlements:` block for the `Planner` target with `com.apple.developer.icloud-container-identifiers` and `com.apple.developer.icloud-services: [CloudKit]` (mirrors the existing `info:` block pattern already in `project.yml`).
2. Add `UIBackgroundModes: [remote-notification]` to the iOS Info.plist properties (CloudKit sync uses silent push to notify other devices of remote changes).
3. In `PlannerApp.swift`, switch to `ModelConfiguration(schema: schema, isStoredInMemoryOnly: false, cloudKitDatabase: .automatic)`, and if that container init throws, catch it and retry with a local-only `ModelConfiguration` (no `cloudKitDatabase:`) before falling back to `DataLoadErrorView` — so a missing/misconfigured entitlement degrades to local-only instead of an error screen.
4. Test with two simulators (or a simulator + device) signed into the *same* iCloud account in Settings.

## App icon

[Planner/Assets.xcassets/AppIcon.appiconset](Planner/Assets.xcassets/AppIcon.appiconset) has real artwork, not a blank placeholder: a white calendar-page card (with binder rings) on a blue gradient background, showing the app's own hourly-grid lines and one accent-orange scheduled-task block — a deliberate choice to reflect this app's actual UI rather than a generic calendar glyph. It was generated, not hand-drawn in an image editor: a standalone Core Graphics script (run once via `swift <file>.swift`, not checked into the repo — the rendering logic is straightforward to reproduce from this description if it ever needs regenerating) rendered a 1024×1024 master twice — once full-bleed for iOS (which applies its own corner mask) and once pre-clipped to an approximate macOS squircle (a rounded-rect with `cornerRadius = 0.225 * size`, not Apple's exact superellipse math, but visually close) — then `sips` downscaled the mac master to every pixel size `Contents.json` needs (16/32/64/128/256/512/1024), with `Contents.json` pointing multiple idiom/scale entries at the same file where the pixel size coincides (e.g. mac 32×32@1x and 16×16@2x are both 32px, same file). Verified two ways: build succeeds with no asset-catalog warnings, and — since this environment can't navigate the simulator's home-screen pages without touch input — `NSWorkspace.shared.icon(forFile:)` against the built macOS `.app` was used to confirm Launch Services actually resolves the custom icon rather than falling back to a generic one.

## Architecture

**Data model** — single SwiftData `@Model`, [Planner/Models/PlannerTask.swift](Planner/Models/PlannerTask.swift). Named `PlannerTask`, not `Task` — the spec's data model calls it `Task`, but that collides with Swift's concurrency `Task` type, so every reference in code and views uses `PlannerTask`. Default reminder offset is 15 minutes (`reminderMinutesBefore`). `recurrenceParentId`/`recurrenceRule` (both optional, matching spec field names) support recurring tasks — see below. `startMinute: Int` (0/15/30/45, default 0) gives start time 15-minute granularity alongside `startHour`; it was added as a **purely additive field with a default**, specifically to avoid the rename/type-change migration pitfall noted below — verified on-device that pre-existing rows (implicitly `startMinute = 0`) load correctly alongside newly-created rows that set it, no migration needed.

**Selected-date querying + day navigation** — [Planner/Views/ContentView.swift](Planner/Views/ContentView.swift) queries *all* `PlannerTask` rows (sorted by date then hour) and filters to `selectedDate` client-side via a computed property, rather than a SwiftData `#Predicate` scoped to one day — this is what makes prev/next-day and jump-to-date cheap (`selectedDate` is just `@State`, no query re-init needed). Day navigation has three paths, all changing the same `selectedDate`: toolbar chevrons, a calendar-icon button opening `DateJumpView` (a graphical `DatePicker` sheet), and a horizontal swipe gesture on the grid content (`daySwipeGesture`, using `.simultaneousGesture` with an angle/distance threshold so it doesn't fight the grid's own vertical `ScrollView`). `HourlyGridView` takes an `isViewingToday` flag so the current-time red line and current-hour highlight only show when actually viewing today.

**Hourly grid layout** — [Planner/Views/HourlyGridView.swift](Planner/Views/HourlyGridView.swift) renders hour rows as a background `VStack`, then overlays task blocks in a `GeometryReader` layer positioned by absolute `.offset(x:y:)` computed from `startHour`/`startMinute`/`durationMinutes` — this is a manual calendar-day-view layout, not a `List`/`LazyVGrid`. Grid range (7 AM–7 PM) and row height live in [Planner/Support/GridConfig.swift](Planner/Support/GridConfig.swift); change the visible hour range there. Each hour row draws three faint, unlabeled quarter-hour tick marks (:15/:30/:45) as a visual reference for off-the-hour task placement — the hour gridline/label is the only labeled one. **Past bug**: [TaskBlockView.swift](Planner/Views/TaskBlockView.swift)'s content used `.frame(maxWidth: .infinity, alignment: .topLeading)` — no `maxHeight`. That stretches width but not height, so the colored background only ever grew to fit the text (~46pt) regardless of the outer `.frame(height: blockHeight)` HourlyGridView reserved for it; every task looked capped at roughly the same short height, most visible on long tasks (a 2-hour task rendered no taller than ~30 minutes). Fixed by adding `maxHeight: .infinity` alongside `maxWidth: .infinity`. If block heights ever look wrong again relative to duration, check that modifier first before suspecting the `blockHeight(for:)` math. **Past bug**: the hour divider `Rectangle` in `hourRow(_:)` had `.padding(.top, 4)`, so the visible gridline for "9 AM" sat 4pt *into* that row rather than exactly at the row's top edge (the true hour boundary, since rows are a zero-spacing `VStack`) — meanwhile task blocks were positioned via `yOffset(for:) + 2`, i.e. only 2pt into the row. The 2pt gap between the two made blocks look slightly misaligned with the clock. Fixed by removing the divider's padding entirely (it now sits exactly at the true boundary) and giving the label its own cosmetic `.offset(y: -7)` to visually straddle the line instead — and by making the block's own inset symmetric (`yOffset(for:) + 1`, `blockHeight` shrunk by `2` instead of the old asymmetric `+2`/`-4`) so a block's center, not just one edge, tracks the true slot.

**Overlap layout** — [Planner/Support/TaskLayout.swift](Planner/Support/TaskLayout.swift) implements interval-graph-coloring to give overlapping tasks side-by-side columns (standard calendar-app technique), keying off `startHour * 60 + startMinute` (not just `startHour`) so two tasks that overlap only because of their minute offsets — e.g. a 9:00–10:00 and a 9:15–9:45 — are correctly detected and column-split. `HourlyGridView` calls `TaskLayoutEngine.layout(for:)` and uses the returned `column`/`columnCount` to compute each block's width and x-offset. If task blocks ever overlap visually, this is the file to check.

**Add/Edit** — [Planner/Views/AddEditTaskView.swift](Planner/Views/AddEditTaskView.swift) is one sheet used for both create and edit, keyed by whether an `editingTask: PlannerTask?` was passed in. An Hour picker and a separate Minute picker (`GridConfig.minuteOptions`: :00/:15/:30/:45) sit side by side in the "When" section. Field defaults (duration 60 min, reminder 15 min before) come from `GridConfig`/`PlannerTask`. Recurrence (the Repeat picker, custom-weekday selector, end-date toggle) only appears when creating a *new* task, not editing an existing occurrence. **Past bug**: `GridConfig.durationOptions` was `[15, 30, 45, 60, 90, 120]` — a 30-minute jump from 60→90→120 even though the rest of the app (drag-resize, `startMinute`) is 15-minute granular. Fixed to `[15, 30, 45, 60, 75, 90, 105, 120]`, consistent 15-min steps throughout. `durationLabel(_:)` was also switched from decimal-hour formatting (`"1.5 hr"`) to `"1 hr 15 min"` style, since decimals get ambiguous once there's more than one non-round option in the list.

**Recurring tasks** — a recurring task is **not** one row with a repeat rule; it's many independent `PlannerTask` rows (one per occurrence) sharing a `recurrenceParentId`, generated by [Planner/Support/RecurrenceEngine.swift](Planner/Support/RecurrenceEngine.swift). This is deliberate: `isCompleted`/`checkInSent`/reminders are per-row fields, and a daily standup needs its Monday completion independent from Tuesday's — a single row with a rule couldn't represent that without a much bigger redesign. `RecurrenceRule` (`frequency: .daily | .weekly | .weekdays | .custom(days: [Weekday])`, plus optional `endDate`) matches the spec's data model, but as of the incident #2 fix (see "Rebuilding without losing data" above) it's no longer what SwiftData actually persists — `PlannerTask.recurrenceRule` is a computed property bridging to flat `recurrenceFrequencyRaw`/`recurrenceCustomDays`/`recurrenceEndDate` fields, since storing the `RecurrenceRule`/`RecurrenceFrequency` enum-with-payload directly was the root cause of a real crash. Everything below still reads/writes `task.recurrenceRule` as before; this is purely a storage-layer change. Occurrences are materialized `RecurrenceEngine.materializationWindowDays` (60) ahead — capped earlier by `endDate` if the rule has one — at creation time in `AddEditTaskView.save()`, and topped up on every launch/foreground by [Planner/Support/SeriesEditor.swift](Planner/Support/SeriesEditor.swift)'s `topUpAllSeries(context:)` (called from `ContentView.task`/`.onChange(of: scenePhase)`).
- **Why notifications are capped separately from materialization**: `UNUserNotificationCenter` hard-limits an app to 64 pending local notifications *total*. A single daily series materializing 60 days ahead would need up to 120 requests (reminder + check-in per occurrence) on its own. So `NotificationScheduler.reschedule(for:)` is only called for occurrences within `RecurrenceEngine.notificationHorizonDays` (7) — `topUpAllSeries` is what "graduates" a previously-out-of-horizon occurrence into having real notifications once today rolls close enough to it. Verified via a temporary debug harness: a 60-day daily series materialized exactly 61 rows, of which only the 8 within the 7-day horizon triggered `reschedule(for:)`.
- **Editing and deleting a series occurrence both ask "this occurrence only" vs "this and future occurrences"** (matches spec's Milestone 6 requirement), via `confirmationDialog`s in `AddEditTaskView`. The cascade logic (`SeriesEditor.applyEditToThisAndFuture` / `deleteThisAndFuture` / `deleteEntireSeries`) fetches siblings by `#Predicate<PlannerTask> { $0.recurrenceParentId == targetID }` — this was specifically verified via debug harness since SwiftData's `#Predicate` macro has known rough edges with Optional-typed property comparisons; it works correctly here as long as the comparison value is captured as a local `UUID?` (not a bare `UUID`) before being used in the predicate closure.
- Only the *editable fields* (title/notes/hour/duration/reminder) cascade on "this and future" — the recurrence pattern itself (frequency/custom days/end date) can't be changed after creation in this v1; each occurrence also keeps its own `scheduledDate`/`isCompleted`/`checkInSent` regardless of cascade scope.
- Voice entry deliberately does **not** support setting recurrence — the spec explicitly keeps "natural language for complex recurring phrases" out of scope even though manual recurrence is in. `VoiceEntryView` always creates a single one-off task (`recurrenceParentId` nil).

**Drag-to-move / drag-to-resize** — [Planner/Views/DraggableTaskBlock.swift](Planner/Views/DraggableTaskBlock.swift) wraps `TaskBlockView` with a **single** `DragGesture` on the whole block, which classifies itself as move/resizeTop/resizeBottom from `value.startLocation.y` (the point where the touch *began*, stable for the whole gesture) — grabbing within `edgeGrabZone` (14pt) of the top or bottom edge resizes, anywhere else moves. Move keeps duration fixed and snaps to 15-minute increments (matching `startMinute`'s granularity); top-edge resize keeps the *end* time fixed (moves start, shrinks/grows duration to compensate); bottom-edge resize keeps the *start* time fixed. Dragging only updates local `@State` for a live preview (offset/height); it never touches SwiftData itself — it just reports the proposed new values via `onCommit` when the drag ends, so a single drag doesn't spam writes or reschedule notifications every frame. Works identically for touch (iPhone) and mouse/trackpad (Mac) since `DragGesture` is platform-generic. The snapping/clamping math (15-min move, 15-min resize, end-time-anchored top-resize, range clamping, edge-zone classification) was verified via standalone `swift` scripts since drag gestures can't be exercised in this headless environment.

**Past bug 1**: the gesture(s) were attached via `.gesture(...)`, which lost to `HourlyGridView`'s enclosing `ScrollView`'s own native vertical-pan gesture — dragging a block just scrolled the page instead of moving/resizing it, since both are vertical drags and the ScrollView's built-in recognizer had priority. Fixed by switching to `.highPriorityGesture(...)`, which lets the block's own drag win once a touch starts on it; a stationary tap still passes through to `TaskBlockView`'s `.onTapGesture` underneath since a `DragGesture` with `minimumDistance` never "recognizes" a non-moving touch. **Past bug 2**: the original design used *three separate* overlapping views (the body plus two thin resize-handle strips), each with its own `.highPriorityGesture`. Bottom-edge resize specifically stayed unreliable even after the ScrollView fix — never fully root-caused (couldn't reproduce without touch input to instrument it), but multiple stacked sibling views each independently claiming gesture priority is exactly the kind of setup where SwiftUI's gesture disambiguation gets subtle. Replaced with the current single-gesture-plus-start-location-classification design, which is the standard, more robust pattern for "edge vs. body" drag interactions and has no overlapping recognizers to conflict in the first place. If a drag-related bug resurfaces, suspect gesture-priority/overlap issues generally — this class of bug has bitten this feature twice.

`ContentView.retime(_:newStartHour:newStartMinute:newDurationMinutes:)` is where `onCommit` actually lands — for a one-off task it applies immediately; for a task with `recurrenceParentId != nil` it instead stashes the proposed values in `pendingRetime` and shows a `confirmationDialog` ("This Occurrence Only" / "This and Future Occurrences"), matching the Add/Edit sheet's save-scope choice. "This and Future" reuses `SeriesEditor.applyEditToThisAndFuture` (already proven correct via an earlier debug harness) with the *dragged* task's own current `title`/`notes`/`reminderMinutesBefore` — a drag never touches those fields, only time/duration. One known rough edge: because `DraggableTaskBlock` always resets its local drag-preview state in `onEnded` regardless of what the caller does with `onCommit`, a recurring-task drag visually snaps back to its pre-drag position for an instant before the dialog result (if any) re-applies the new position — cosmetic, not a correctness bug, not worth the added complexity of threading dialog-pending state back down into the drag view.

**Notifications** — [Planner/Notifications/NotificationScheduler.swift](Planner/Notifications/NotificationScheduler.swift) is the single place that computes reminder/check-in trigger dates and schedules/cancels them; every create/edit/delete/complete-toggle path (in `AddEditTaskView` and `ContentView`) calls into it rather than touching `UNUserNotificationCenter` directly. Both a task's reminder and its completion check-in are identified by `"reminder-\(task.id)"` / `"checkin-\(task.id)"`, so `reschedule(for:)` can always cancel-then-recreate idempotently. [Planner/Notifications/PlannerNotificationDelegate.swift](Planner/Notifications/PlannerNotificationDelegate.swift) handles the check-in's Yes/No actions — it deliberately opens its own `ModelContext(modelContainer)` rather than using `mainContext`, because delegate callbacks can land on a background queue and `mainContext` is meant for the main actor. **Known constraint**: local notifications don't appear in `pendingNotificationRequests` (and by extension won't display) until the user has answered the system permission prompt at least once — this can only be verified by a human tapping "Allow"/"Don't Allow" in the simulator, which this environment couldn't do headlessly (see Testing section below).

**Voice entry** — [Planner/Voice/SpeechRecognizer.swift](Planner/Voice/SpeechRecognizer.swift) wraps `SFSpeechRecognizer` + `AVAudioEngine` behind a small `@MainActor` `ObservableObject`; [Planner/Support/SpokenTaskParser.swift](Planner/Support/SpokenTaskParser.swift) is pure, dependency-free logic that pulls a spoken time out of a transcript via `NSDataDetector` (not hand-rolled regex/NLP) — including the minute, snapped to the nearest quarter-hour via `GridConfig.minuteOptions` — and strips the matched phrase to produce a clean title. If no time is detected, [Planner/Views/VoiceEntryView.swift](Planner/Views/VoiceEntryView.swift) falls back to `GridConfig.nextOpenSlot(for:from:minute:)`, which walks 15-minute slots (not just whole hours) to find the next unoccupied one. Voice-created tasks land on whatever `selectedDate` the grid was showing when the mic button was tapped (`targetDate` param), not always today. `AVAudioSession` calls in `SpeechRecognizer` are `#if os(iOS)`-gated since that type doesn't exist on macOS. **Past crash**: `startRecording()` used to pass `inputNode.outputFormat(forBus: 0)` straight into `installTap` with no validation. `installTap` raises a hard Objective-C exception — not a Swift `Error`, so `try/catch` can't stop it — if that format is degenerate (zero sample rate/channel count), which can happen right after the audio session activates, before the route has settled. This crashed the app immediately after the mic permission prompt was answered. Fixed by validating `recordingFormat.sampleRate > 0 && recordingFormat.channelCount > 0` before calling `installTap`, throwing `RecognizerError.audioUnavailable` (already handled by `VoiceEntryView`'s catch) instead of letting it reach the crash. This couldn't be reproduced in this environment (no working microphone route in the simulator, and speech-recognition authorization can't be pre-granted headlessly — see Testing section), so if voice entry crashes again, get a crash log/stack trace rather than assuming this exact fix covers it.

## Testing constraints in this environment

Several things can't be exercised headlessly here and had to be verified by other means — worth knowing before assuming something is broken:
- **No simulator tap/touch input.** The native `mcp__Claude_Code_iOS_Simulator__control` tool needs `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`, which needs an interactive password prompt. So sheet flows, gestures (including the day-swipe), and permission prompts are verified by code review + build success + screenshot of the rendered state, not by actually driving the UI.
- **No Mac UI-scripting/accessibility access either.** `osascript`/System Events can't drive the Mac app's UI (`osascript is not allowed assistive access`, error -1728, granting it needs an interactive System Settings prompt) — confirmed while investigating incident #2 above. So the Mac app can be launched, killed, focus-toggled (`osascript ... to activate` on other apps still works, since that's not scripting *into* Planner), and its process/crash-log state inspected, but its actual UI (clicking buttons, filling in the Add/Edit sheet) can't be driven headlessly. This is why incident #2's exact crash trigger couldn't be directly reproduced — only inferred from the crash log plus a standalone (non-UI) SwiftData harness.
- **`simctl privacy` doesn't cover notification or speech-recognition authorization** (only TCC services like microphone, camera, contacts, etc. — confirmed by checking `xcrun simctl privacy grant --help`'s service list). So those permission prompts can't be pre-granted headlessly either; they need a real tap.
- Where useful, pure logic (`SpokenTaskParser`, `RecurrenceEngine.occurrenceDates`) was verified by running it standalone via `swift <file>.swift` outside the simulator entirely — no SwiftUI/UIKit/SwiftData needed, fast, and a good pattern to reuse. Logic that *does* need SwiftData (e.g. the `recurrenceParentId` predicate, the edit-scope cascade, the SchemaV1→V2 migration) was verified via a temporary debug harness added to `PlannerApp.swift`, run once via a launch argument, then removed — grep the git history for `-seedEditScopeTest`/`-seedRecurringTest`/`-debugDumpAllTasks` if you need the pattern again — or, for logic that doesn't need a *running app* at all (just SwiftData itself), by copying the relevant source files to a scratch directory and building a throwaway binary with `swiftc` (name the entry-point file `main.swift`; `container.mainContext` is `@MainActor`-isolated so use `ModelContext(container)` instead in a plain script). This is how incident #2's root cause was confirmed and the fix validated without touching the real app or its data.
- **On macOS, check `~/Library/Logs/DiagnosticReports/<AppName>-*.ips` for a real crash log before re-theorizing a crash.** It's JSON; `lastExceptionBacktrace` and the `threads` array (find the one with `"triggered":true`) show exactly where and why. This is what actually solved incident #2 — direct evidence beat several rounds of plausible-but-unconfirmed theories in incident #1.
